## 当前边界

| 项目 | 已知情况 | 不能据此承诺 |
| --- | --- | --- |
| Alpha 未读快照 | 使用未读数量与末条构造范围，分页前后复核并重试 | 数据库级原子快照、任意并发读取下永不变化 |
| Alpha 与微信状态 | 群岛以 Alpha 会话未读为来源 | Alpha 的状态一定与微信即时一致 |
| 实时推送 | SSE 连接加补查恢复 | SSE 具备可靠历史重放或永不漏流 |
| 模型质量 | 有格式、证据和流程测试；有部分真实调用记录 | Jev 相关性准确率或所有摘要质量已验收 |
| 超上下文 | 完整分段覆盖有自动化验证 | 长文本汇总的真实内容质量已充分验证 |
| 长期运行 | 有恢复与账号隔离测试 | 持续高流量、跨多次休眠、多显示器动画均已全面实测 |
| 本地隐私 | 状态及诊断按要求包含原文，文件有限权 | 原文已经加密或移出白名单能撤回已发送请求 |
| 历史记录 | 升级不删除已有摘要与日志 | 历史范围外内容出现就说明新版仍在采集 |
| 原文展示 | 文字与媒体占位可读，没有微信发送入口 | 完整支持所有媒体渲染或微信客户端功能 |

最近一次未读质疑已由用户确认属 Alpha 并停止排查，见 [D10](07-决策记录.md)。以下是未来问题的排查方法，不是继续执行该已停止任务。

## 排查原则

先接受用户报告的现象，沿代码和数据链路找证据；不要仅凭一次接口相等、测试通过或截图相似就宣布没有问题。也不要为了交付而进行与根因无关的试探性修改。

需要 UI 时只验证具体交互，优先核对账号、群、请求时间、响应字段与状态更新顺序。不要让用户反复举例证明已有反馈；确实缺信息时一次性说明缺少什么。没有证据支撑时明确仍未定位，不归咎上游或用户。

## 常见现象与检查入口

| 现象 | 检查顺序 | 代码 / 日志入口 |
| --- | --- | --- |
| 消息没有进入处理 | 当前账号 → 群标识 → 白名单 → 去重键 → 缓冲截止 | `MessageAdmission`、`PushMessage`、`实时缓冲 flush` |
| 无关消息触发即时摘要 | 本地命中依据 → 是否群体提醒 → Jev 概率及阈值 → 任务真实来源 | `本地决策`、`整批决策路由`、`摘要入队` |
| 相关但需要关注里没有 | 直接提醒配置 → Jev 是否只提交摘要 → 模型是否完成 → `related` / 证据 → 已阅状态与账号 | `JevMonitor`、`persistSummary`、`AttentionFeed` |
| 周期反复摘要同一范围 | 实际末条与持久化成功末条 → 保存是否失败 → 重试来源 | `周期扫描`、`SummaryState.markers`、`SnapshotPersistence` |
| 原文缺失或数量不够 | 完整 Alpha 分页 → 时间边界 → 快照证据 → 弹窗消息合并 | `UnreadSnapshotLoader`、`ConversationMessages`、`ChatTranscript` |
| 旧未读被排除 | 检查是否把成功标记误用为输入过滤条件 | `SummaryCoordinator`、`SnapshotSummarizer` |
| 执行中新消息被误标成功 | 固定快照末条与实际保存标记是否一致 | `固定未读快照`、`摘要完成，成功标记已保存` |
| 移出群后仍处理 | 取消代次、白名单再校验、恢复批次及任务来源 | `setWhitelist`、`retainGroups`、`JevMonitor` |
| 日志不即时更新或跳页 | 是否落盘成功 → 事件订阅 → 跟随状态 → 历史游标 | `DiagnosticLogStore`、`LogsPage` |
| 已阅历史仍有小点 | 先确定页面；关注点看 pending，摘要「微信 N」看 Alpha | `AttentionThread.pendingCount`、`ConversationUnreadState` |

在 Jev 模式中，“判断相关”与“摘要已经成功生成”不是同一事件。只判断相关但不需要立即回应的消息可能先排入摘要队列，相关摘要完成后进入关注流；不可用两种事件的不同时间断言结果丢失。

## 新的未读同步问题

当前实现由 [GroupStateSynchronizer](../Sources/QundaoCore/GroupStateSynchronizer.swift) 协调同账号读取，[AppStore](../Sources/Qundao/Stores/AppStore.swift) 独立轮询：每次读取结束后等待 5 秒，而不是保证每 5 秒完成一次。打开窗口、激活和唤醒会请求刷新，暂停消息监听仍保留未读刷新。

首次同步前显示未知；失败保留上次状态并显示失败提示与手动刷新入口。排查时分别核对请求是否发出、是否完成、结果是否被丢弃 / 覆盖，以及 UI 读的是微信未读还是本地待阅。慢请求、错误或取消只是检查方向，不应在没有复现证据时写成根因。

用户在群岛点已阅后微信计数不变是已确认行为；如果 Alpha 的 `unread_count` 已变化而群岛没有变化，则应检查群岛同步与状态绑定，而不是改本地已阅规则。

## 排错时的数据保护

使用只读请求与合成消息测试。不要为复现改变真实白名单、发送微信消息、批量已阅、删除状态或重置用户配置；不要输出完整真实日志。需要看诊断时按关联编号和群范围缩小读取，分享结论时隐藏密钥及无关原文。

证据不足或用户要求停止时，记录已检查范围、未证实假设和是否改过代码。排查结束后不能把未实施建议写成产品现有能力。
